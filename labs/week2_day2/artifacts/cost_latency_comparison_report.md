## 1. Summary

- **All three models answer Harbor's questions about equally well; they differ in cost and speed.**
  - On the same 55 questions, with the same agent and only the answer-writing model changed:
    - Haiku 4.5: 51/55;
    - Sonnet 5: 52/55;
    - Opus 5 (reasoning): 53/55.
  - The same Haiku setup scored 50-51/55 across three separate runs, so a 2-question spread is
    **inside run-to-run noise**.
  - What does differ: Opus costs **4.2× Haiku per question** ($0.0121 vs $0.0029) and is **~2.9 s
    slower at the median** (8.1 s vs 5.2 s).
- **Cost per interaction, which is the number finance asks for:**

  | | Haiku 4.5 | Sonnet 5 | Opus 5 |
  |---|---|---|---|
  | Mean $ per member question | **$0.0029** | **$0.0061** | **$0.0121** |
  | p95 | $0.0044 | $0.0107 | $0.0232 |

  Each figure includes every call the question caused: the gate, any query rewrites, the answer.
  Every LLM call went through one instrumentation wrapper and is summed under one ID per question.
- **The agentic behaviour held on every model:**
  - the gate made the right retrieve / don't-retrieve call on **55/55** questions;
  - all 4 unanswerable or restricted questions ended "not in the corpus" rather than a guess;
  - 0 restricted or wrong-tenant documents were cited;
  - every reply named its source.
- **The cache works, and its equivalence rule is strict on purpose.**
  - A warm rerun cost **$0** at **1.7 s** median latency, against 5.2 s cold.
  - Probes confirmed: rewording case or spacing hits the cache; paraphrases, the other tenant, or a
    new corpus version miss.
- **Recommendation for Harbor: Haiku 4.5 as the default generator** (section 9). It's the cheapest and
  fastest, and on this evaluation it's as accurate as the others. Opus only earns its cost if a larger,
  harder evaluation shows it pulling ahead on multi-part questions, which is where its three extra
  answers came from.

## 2. What was built

Day 1's retrieval (hybrid keyword + vector search over Harbor's 27 documents, reranked by a
cross-encoder) became a tool that an agent chooses to use, instead of a fixed first step:

```
member question ──▶ GATE (LLM) ── answer directly ──▶ reply + "general information" source line
                        │ retrieve (writes its own search query)
                        ▼
                 RETRIEVE (Day 1 hybrid + rerank, local)  ◀──────────┐
                        ▼                                            │ rewrite (LLM), told why
                 VALIDATE: rerank score ≥ 0.10?  ── no ──────────────┤ the round failed
                        │ yes                                        │ (max 3 rounds)
                        ▼                                            │
                 GENERATE (LLM): grounded answer, or decline ─ decline / bad citation
                        │ answered                                   │
                        ▼                                   after round 3: "not in the corpus"
                 reply + code-built source line (title, version, effective date)

  every LLM call: wrapper → record → exact-match cache → spend guard → Anthropic API
```

- **Two layers of relevance checking.**
  - Layer 1 (reranker threshold) rejects off-topic results without an LLM call.
  - Layer 2 (the generator) declines near misses, such as auto-loan rules given for an RV-loan
    question.
  - Either failure sends the agent back to rewrite its query, up to 3 rounds. The cap is in code,
    not in a prompt.
- **Instrumentation rules** (tested, so a violation fails the test suite):
  - one file owns the only API client;
  - no call can run without a question ID;
  - every call writes one record, including cache hits and errors;
  - local model steps are recorded at $0 with their real latency.
- **A spend guard** stops every provider call once the day's ledger reaches $3.50. The day's total was
  $2.58 (section 10).

## 3. Setup

**Task.** Answer a member question from Harbor's documents with a cited, version-correct answer, or
answer directly without documents, or say it isn't in the corpus.

**Eval set: 55 questions.**
- Day 1's golden set, unchanged: 45 questions (41 answerable, 3 unanswerable, 1 whose only answer is
  in a restricted document).
- **10 new questions where retrieving is the wrong move**: greetings, "am I talking to a person?",
  arithmetic, "what does APR stand for?", off-topic requests.
- Each question runs as a member-facing request: its own tenant, restricted documents excluded,
  superseded policy versions excluded.

**What changes between runs: only the generator.** The gate and query rewrite are Claude Haiku 4.5 in
every run. The grader is Claude Sonnet 5 in every run.

| Candidate | Model | Thinking | Why |
|---|---|---|---|
| A | Claude Haiku 4.5 | none | Low-cost baseline |
| B | Claude Sonnet 5 | explicitly disabled | Mid tier, no deliberation |
| C | Claude Opus 5 | adaptive, **effort = medium**, **max_tokens = 4,000** | The reasoning model |

**The thinking budget, stated plainly.** Current Claude models reject a fixed thinking-token budget:
`budget_tokens` returns HTTP 400 on Sonnet 5 and Opus 5. Opus 5's thinking budget was therefore set by
two explicit controls:
- `output_config.effort = "medium"`: how much the model deliberates;
- `max_tokens = 4000`: a hard ceiling on thinking plus answer tokens per call.

Thinking tokens are billed as output tokens and are included in every recorded `output_tokens` figure.
Medium was fixed before the full run by a rule set in advance: the 5-question pilot projected $0.74
for Opus over 55 questions, under the $1.20 allowance. It was not raised afterwards. No call hit
max_tokens.

**Prices** (USD per million tokens, pinned 2026-09-25):

| Model | Input | Output | 5-min cache write | Cache read |
|---|---|---|---|---|
| Haiku 4.5 | 1.00 | 5.00 | 1.25 | 0.10 |
| Sonnet 5 | 2.00 | 10.00 | 2.50 | 0.20 |
| Opus 5 | 5.00 | 25.00 | 6.25 | 0.50 |

**Tokenizer caveat.** Sonnet 5 and Opus 5 use a newer tokenizer that turns the same text into more
tokens: +35% measured on our smoke prompt (164 vs 221 tokens). Compare the models in **dollars**, not
token counts.

**How quality is graded.**
- *Task success* (the headline): the right outcome for the question type. An answerable question also
  needs the judge's verdict "correct" **and** a citation of a chunk containing the expected passage.
- *LLM judge:* Sonnet 5 compares each answer with Harbor's reference answer (correct / partial /
  incorrect). The judge prompt was revised once after calibration (section 8).
- *Deterministic checks:* gate decision, outcome, citation, leaks, version in force, source line.

**Reproduce for $0.** Every LLM response is stored in `cache/llm/`, which is committed. For example:

```
uv run python src/run_eval.py --generator opus --namespace C --replay-of runs/20260928-075936_opus_C
```

Run with no API key, this reproduced all 55 answers, citations and grades **identically**.

the thinking, if the visible answers are the same length. These are short factual questions, and Opus
spent little effort deliberating over them.

## 5. Cost per interaction

**Where the money goes** (sum over the 55 questions, per run):

| Purpose | Haiku | Sonnet | Opus |
|---|---|---|---|
| Gate (Haiku in every run) | $0.052 | $0.053 | $0.052 |
| Query rewrites (Haiku) | $0.010 | $0.011 | $0.008 |
| Answer (generator) | $0.089 | $0.256 | $0.577 |
| Direct answer (generator) | $0.006 | $0.017 | $0.029 |
| **Total for 55 interactions** | **$0.157** | **$0.337** | **$0.666** |
| Gate's share of cost per interaction | ~36% | ~19% | ~11% |

**What makes a question expensive:**
- **Long, multi-part answers.** The top 3 on Sonnet and Opus were q032-q034 (Opus: $0.029-$0.030 each,
  ~860-920 output tokens).
- **Extra retrieval rounds.** Haiku's most expensive question was unanswerable q043: 3 rounds and 4 LLM
  calls, $0.0049.
- **The cheapest questions** were the no-retrieval ones: 2 calls, no retrieval ($0.0014 on Haiku).
- **The bound on cost.** The worst case per question is fixed by the design: 1 gate + 2 rewrites + 3
  answer attempts.

**Provider prompt caching** (Anthropic's discounted cache reads, *not* free):
- It only applies above a model's minimum prompt length: 512 tokens for Opus 5, 1,024 for Sonnet 5,
  4,096 for Haiku 4.5.
- Our answer prompt (~850 tokens) cleared Opus's minimum only.
- Opus wrote 1,367 tokens to the cache and read 41,271 cached tokens at $0.50/M instead of $5.00/M.
  That saved about **$0.19** on the run, about $0.0034 per question.
- **Without it, Opus would cost ~$0.0155 per question.**
- The wrapper priced cache reads at the discounted rate, as the lab requires.

**Monthly projection.** This assumes **5,000 questions/day** and the same mix of questions as this eval
(18% with no retrieval). Both are *assumptions* for scale, not Harbor data.

| | Haiku 4.5 | Sonnet 5 | Opus 5 |
|---|---|---|---|
| $/month | ~$430 | ~$920 | ~$1,820 |

Local-cache hits would lower all three in proportion to how often members repeat questions word for
word.

|---|---|---|---|

- Latency was measured on one laptop at one time of day. Treat it as relative between models, not as
  a service-level figure.

## 7. Agentic behaviour

**Gate: 55/55 on every run** (165/165 across the three Haiku runs). Each decision is logged with a
reason, for example: *"The member is asking about a specific Harbor fee, which requires checking
Harbor's fee schedule."* The 10 no-retrieval questions were answered directly, with no fee or rate
quoted and a "general information, not from Harbor's documents" source line.

**Rounds per question:**

| Generator | 0 rounds (direct) | 1 round | 2 rounds | 3 rounds |
|---|---|---|---|---|
| Haiku | 10 | 40 | 0 | 5 |
| Sonnet | 10 | 39 | 1 | 5 |
| Opus | 10 | 41 | 0 | 4 |

**Not in the corpus.**
- **q043, q044, q045:** safe-deposit rent, crypto custody, RV-loan prepayment.
- **q003:** its only answer is in a restricted fraud document.

All four ended "not in the corpus" on every model. q045 is the hard one: Day 1 showed its auto-loan
near miss outscores 12 answerable questions. It was caught by the layered check:
- rounds 1-2: the reranker rejected the auto-loan chunks for the agent's queries;
- round 3: one chunk passed at 0.18, and the generator declined it: *"The passage provided is about
  auto loans, not RV loans."*

**A worked rescue** (q024, validator sweep run τ = 0.05, $0.0053, 8.9 s):
1. **Gate:** retrieve. Query "auto loan approval time mobile app".
2. **Round 1:** 3 chunks kept (top 0.94). The generator answered, but cited the chunk ID wrapped in
   square brackets. The citation guard blocked it as *ungrounded*.
3. **Rewrite:** "how long does auto loan approval take".
4. **Round 2:** the generator answered with a valid citation: *"On average, auto loan approval through
   the mobile app takes 0.6 business days."*
   `Source: Auto Loan Product Comparison (version 2026-09, effective 2026-09-01), p.1 [includes a
   model-generated figure caption]`

The rescue path worked as designed. The honest reading: the round-1 block was a **citation formatting
slip, not a hallucination**. Accepting bracketed IDs is listed under gaps (section 11).

**Version in force (q028-q031).**
- Every model cited only Overdraft Policy v3, and every reply's source line names "version 3.0,
  effective 2026-01-01".
- Opus's q028 answer also said the fee "was reduced from $32 under the previous version 2.0". That's
  accurate, and it comes from v3's own change history.
- The strict rule set before the run ("never names version 2") counts it as a failure, giving
  **version_quoted 0.75 on Opus** and 1.0 on the others. A human reading finds it correct and clearly
  labelled.
- The rule was not changed after the results. A better rule would reject v2 only when it's presented
  as current.

**Validator threshold sensitivity** (Haiku, three runs):

| τ_keep | Task success | Rounds 0/1/2/3 | $/interaction | Wrongly declined |
|---|---|---|---|---|
| 0.05 | 51/55 | 10/39/2/4 | $0.0030 | 0 |
| **0.10** (used) | 51/55 | 10/40/0/5 | $0.0029 | 1 |
| 0.30 | 51/55 | 10/40/1/4 | $0.0027 | 0 |

- The threshold made no measurable difference.
- Of 8 questions that failed in any of these runs, only q034 failed in all three. The rest moved
  between runs, because the gate writes a slightly different search query each fresh run.
- That run-to-run variation (±1 question) is the noise band used to read section 4.
- τ = 0.10 was chosen from Day 1's scores against the *member's own* questions. The validator actually
  scores against the *agent's* queries. The agent's queries score correct passages higher and near
  misses lower (Wire Transfer Policy: 0.13-0.33 vs 0.003-0.018), so τ is a sensible default, not a
  calibrated value.

## 8. Judge calibration

**The calibration sheet** (`artifacts/judge_calibration.md`) has 30 cases: 10 per model, with every
non-"correct" verdict from the original judge first. It was graded twice, blind to the judge's
verdicts: first by Claude as a second grader, then **by a human reviewer**. All comparisons are in
`runs/judge_calibration.json`.

**Step 1: the model second grader found systematic errors in judge v1** (24/30 agreement).
- The judge called an omission "incorrect" 4 times, and marked extra true detail "partial" twice.
- Read literally, its written rules say an omission is "partial" and extra detail is fine.
- **Fix (judge v2):** the same rules, written as an explicit order of checks: contradiction →
  omission → correct. Extra detail never lowers the verdict, and a number on the wrong label counts as
  a contradiction.
- All reported runs were re-graded with v2 ($0.49). The agent's answers were not regenerated.

**Step 2: the human check.**

| Agreement with the human | 3-level (correct / partial / incorrect) | Correct vs not correct (what task success uses) |
|---|---|---|
| Judge v1 | 28/30 | 28/30 |
| **Judge v2** (used in this report) | 25/30 | **29/30** |
| Claude second grader | 26/30 | 30/30 |

- **The headline metric is human-validated.** On correct vs not correct, which is all task success
  counts, v2 matches the human on 29/30. The human confirmed v2's key fix: extra true detail is not
  penalised (q015 on Haiku and Sonnet).
- **One disagreement affects a headline:** Sonnet q020. The human said partial ("includes the
  required fact but with information that contradicts the reference"); v2 said correct.
- **On partial vs incorrect, the human agrees with v1, not v2.**
  - The human treated a missing required fact as *incorrect* in 4 of 5 omission cases (q034 on Haiku
    and Sonnet, Sonnet q035, Opus q033), and Opus q034 as partial.
  - v2 follows the rubric text ("an omission is always partial"), so it moved away from the human
    here.
  - This doesn't change any task-success number, since partial and incorrect both fail. But **the
    partial/incorrect split in this report reflects the written rubric, not the human's standard.**
    The rubric should be revised to say which one Harbor wants.

| Task success | Haiku | Sonnet | Opus |
|---|---|---|---|
| Judge v1 | 50 | 50 | 53 |
| **Judge v2 (reported)** | **51** | **52** | **53** |
| Judge v2, adjusted to the human on the 30 checked cases | 51 | 51 | 53 |

All three rows are within the ±1 run-to-run noise, so the conclusion doesn't change. The checked
sample is small (30 of the 121 judged answers across A-C), and it was weighted towards the judge's
non-"correct" verdicts.

## 9. Recommendation

**Use Claude Haiku 4.5 as Harbor's default generator.**
- On this evaluation it matches the others on quality (51 vs 52-53 of 55, within noise).
- It costs **$0.0029 per question, against $0.0061 for Sonnet and $0.0121 for Opus**.
- It's the fastest (5.2 s p50).

Keep the agent design as it is: gate, two-layer validation, 3-round cap, code-built source line.

**When to revisit:**
- **Build a harder evaluation first.** Use more multi-part questions and real contact-centre wording,
  with repeated runs so a 2-3 point difference can be measured. Opus's gains were on multi-part
  questions. If that holds at scale, routing *only* multi-part questions to Opus would buy the
  improvement for a fraction of the cost.
- **If Opus is used, keep effort at medium or lower.** At medium it already thought only lightly on
  these questions. Provider prompt caching cut its cost ~22%, and a longer, stable prompt would
  benefit further.
- **Decide the caption policy.** Sonnet treated a model-generated chart caption as untrustworthy.
  Harbor should decide whether answers may rely on generated captions, and write that into the answer
  prompt.

**Gate adaptation decision: prompt, for now** (full write-up: `artifacts/gate_adaptation_decision.md`).
- The gate is 165/165 accurate at $0.00095 and 1.3 s per call.
- It also writes the search query. That rewording is what makes paraphrases retrievable. A distilled
  classifier couldn't do that.
- A labelled-example bank (RAG) has no headroom to show on this eval.
- **Revisit:**
  - if real-traffic gate errors exceed ~2%, add a labelled-example bank;
  - if volume passes ~35,000 questions/day (under an assumed $1,000/month upkeep), or a latency target
    rules out the ~1.3 s gate, distil it.

## 10. Cache and spend

**The equivalence rule** (when two calls may share a cached answer). Everything that could change the
answer must be identical:
- model and its settings;
- prompt version;
- the full prompt, **including the retrieved evidence**;
- the member's tenant;
- access scope;
- corpus version.

Only the member's question is normalised: case, spacing and trailing punctuation.
- **Why not a semantic cache:** it would treat "overdraft fee" and "overdraft fee for a business
  account", or Overdraft v2 and v3 wording, as the same question. Those are exactly the cases where
  Harbor's answers differ in dollars.
- **No member data in the cache:** entries are keyed on the question and the evidence, never on who
  asked, and the evidence is PII-scrubbed.
- **Hit and miss results are recorded against the key, never the question text.**

| Measurement | Result |
|---|---|
| Cold runs (fresh namespace) | 0% hit rate (every call new) |
| Warm rerun of run A | **100%** of 117 calls hit. $0 per interaction. Latency p50 **1.7 s** (retrieval only) vs 5.2 s cold. Identical answers and grades. |
| Probes: same question, different case/spacing (8) | 8/8 **hit** |
| Probes: paraphrases (5) | 5/5 **miss**: the known price of exact matching |
| Probes: same question, other tenant (3) | 3/3 **miss** |
| Probes: same question, new corpus version (2) | 2/2 **miss** |

Two things surfaced in the probe run:
- **Retries can repeat themselves.** One tenant-swap probe retrieved the same single chunk in all three
  rounds, so the retries sent the generator an identical request. The cache answered them for $0.
  The probes are scored on the first call only, and within-question repeats are reported separately.
- **The tenant filter held.** A business member asking about a *personal* account's wire fee was
  correctly declined.

**Spend** (`runs/spend_ledger.jsonl`, every provider call of the day):

| Item | Spend |
|---|---|
| Smoke tests, traces, pilots | $0.16 |
| Run A (incl. judge) | $0.24 |
| Probes | $0.03 |
| τ sweep | $0.46 |
| Run B | $0.43 |
| Run C | $0.76 |
| Judge v2 re-grade | $0.49 |
| **Total** | **$2.58**, under the $3.50 guard and the $4.00 limit |

The judge (Sonnet 5) cost about $0.002 per graded answer: as much as a whole Haiku question.

## 11. Limitations and known gaps

- **Small sample.** 55 questions, one run per model. Differences under ~3 questions are noise. Latency
  is from one laptop.
- **Judge.** It's LLM-based and in the same family as candidate B. v2 was written after seeing the
  calibration cases. A human check of 30 cases validates it on correct vs not correct (29/30), but not
  on partial vs incorrect (25/30 at 3 levels). The rubric's treatment of omissions needs Harbor's
  decision.
- **The validator threshold** was chosen from Day 1 data on the same golden set.
- **Citation guard too literal.** It rejects a correct chunk ID wrapped in brackets (q024). Fix:
  normalise IDs before checking.
- **Version rule too strict.** It fails a correct answer that mentions v2 as history (Opus q028).
- **Output artifacts.** 8 answers contain text glitches where an em dash belonged: 7 Opus (q001, q008,
  q009, q031, q032 show a literal `\u2014`; q014 a stray `"`; q033 garbled fragments "\ninch", "\nsic")
  and 1 Sonnet (n002, `\u2014`); Haiku has none. The source text is clean, so it's in the models'
  structured-output text. A member would see it. Fix: normalise escape sequences before display, and
  check whether the pinned SDK version is involved. (An earlier, narrower scan found only q033.)
- **Multi-chunk coverage.** q034's "7-10 business days" lives in a different chunk than the rest of the
  answer, and no model found it. That's a retrieval gap, not a model gap.
- **Data leaves Harbor.** Every question and its retrieved (PII-scrubbed) evidence goes to the Claude
  API. Production needs Harbor's vendor approval.
- **Single-turn only.** The cache is safe today because the agent holds no member identity. Member
  context must join the cache key, or bypass the cache, when conversation memory arrives.
