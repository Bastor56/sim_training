Framework comparison matrix

Note: LangGraph was used for this lab. The other compared frameworks are characterized based on their documentation.

| Dimension | LangGraph | AutoGen | Semantic Kernel | Amazon Bedrock Agents | Salesforce AgentForce |
| --- | --- | --- | --- | --- | --- |
| **Orchestration model** | LangGraph is an explicit graph/ state machine. You declare nodes and edges. The control flow is data you can inspect before running it. This is the closest of the open frameworks to a hand-rolled architecture. | AutoGen is a multi-agent ‘conversation’. Agents exchange messages in a group chat. ‘Orchestration’ is which agent speaks next, decided by a selector (usually another LLM call) rather than a specified graph. | Semantic Kernel is a plugin/ planner model. A ‘kernel’ holds registered functions (plugins). A planner decides call order at runtime (this is closer to AutoGen than LangGraph). | Amazon Bedrock Agents provide a managed ReAct-style loop. You declare an agent + action groups (tool schemas via OpenAPI). AWS owns the reasoning loop internally, providing configuration tools rather than a graph you wire. | Salesforce Agentforce is a fully managed platform. Topics/ actions are configured through Salesforce’s builder UI or metadata API. The reasoning loop, model routing, and grounding are entirely platform-owned. |
| ** State management & persistence** | A typed state schema with per-field reducers. Built-in checkpointers (default in-memory, otherwise db options) give free persistence and replay/ ‘time-travel’. | Conversation history is the state, held in-memory per run by default. Longer-term persistence is left to the integrator. | State is split across kernel memory objects and, in the newer process framework, explicit process state. | State/ session persistence is a managed AWS resource (session attributes, DynamoDB-backed by default). You can configure it but you don’t own the schema. | Fully managed inside Salefroce’s data model (Data cloud/ Service Cloud records). There is no separate ‘agent state’ object to reason about at all |
| **Tool integration** | Uses plain python callables as node bodies. There’s no special tool calling abstraction required. An optional pre-built ReAct agent adds standard tool-calling if needed. | Python functions registered per-agent. Tool-calling goes through whichever underlying model API supports function calling. | Uses native “plugins” (i.e. decorated classes/ functions) with automatic function-calling schema generation. | Uses action groups defined via OpenAPI schema or Lambda. Tool integration is a config artifact rather than code you write directly. | Uses “actions” wired to Flows, Apex, or external APIs through a declarative config. |
| **HITL support** | Provides a first-class `interrupt()` primitive that pauses a run mid-graph for human input before resuming from the checkpoint. | Supports a literal human-in-the-loop agent participant in the conversation; however, it’s another chat turn rather than a structured pause/ resume. | HITL emerges in the Process Framework | Native support for user-confirmation steps before executing an action. | Native approval steps and scalation-to-human queues as it’s built on top of Salesforce’s existing case/ queue infrastructure. |
| **Observability hooks** | Has deep integration with LangSmith (traces every node/ edge/ retry). | OpenTelemetry-based tracing in recent versions. | Native OpenTelemetry support. | CloudWatch/ X-Ray integration. Inherits whatever observability discipline the client’s AWS account already states. | Provides what Saleforce’s own agent-monitoring UI exposes. This may be useful for an admin but less transparent for an engineer wanting to trace. |
| **Learning curve** | Moderate – the graph/ reducer/ channel mental model is a real element to learn but it is plain Python underneath. | Low/ moderate – relatively simple to get a demo running; however, the multi-agent conversation model gets harder to predict and debug as the agent count grows. | Moderate/ steep – two overlapping abstractions (plugins vs. the newer Process Framework) and a broader surface area (works with .NET/ Python/ Java). | Low for the happy path (mostly console/ config). However, steep once you need to debug why the managed loop made a given call as you can’t read it’s source. | Lowest for a salesforce admin. Steep/ impossible for an engineer who wants to change something outside of the builder UI. |
| **Enterprise readiness** | Backed by LangChain Inc. & widely adopted but a still fast-moving OSS library. | Backed by Microsoft Research. Multi-agent-first design is a better fit for some workflows than others. Maturity is behind LangGraph’s for single-agent orchestration. | Backed by Microsoft. Multi-language by design. The newer Process Framework is less mature than the plugin model. | Fully managed AWS service with AWS’ usual SLAs/ compliance posture. Readiness is ‘as ready as your AWS account’ rather than a library maturity question. | Fully managed Salesforce service with Salesforce’s compliance posture (plus their pricing/ licensing model). Readiness is a procurement question rather than an engineering one. |

## Build vs. platform-native
A mid-size P&C insurer runs claims and policy servicing inside Salesforce Financial Services Cloud. The adjusters work in Salesforce’s case queues all day.

**Decision:**
Agentforce owns the agent. The claim intake, the human-adjuster handoff, and the approval/ escalation queue are all native Salesforce objects. LangGraph plugs in as a custom action invoked from Agentforce for the fraud-investigation reasoning loop (an unbounded number of cross-checks against external signals) that a declarative action-sequence builder isn’t designed to represent. Agentforce calls out to that action, gets back a decision (plus observation trail), and everything downstream stays inside the platform the client already trusts and audits.
